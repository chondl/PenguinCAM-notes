## Defects

1. **A slice delivered after a timeout or a watchdog stop is silent on the command line
   and in the library's documented use.** `python -m penguin_slice slice` prints only the
   summary; `stop_note` and `memory_note` are on the returned object and nowhere else, and
   the command has no log. Evidence: with the stand-in in `written_then_hang` mode and
   `PENGUIN_SLICE_MAX_PEAK_MB=8`, the command printed the summary and exited 0, although
   the watchdog had stopped the stand-in (it never exits by itself). Through the HTTP face
   the notes reach the server's log line only, which the rulings accept. Fixed when the
   command prints the notes (on stderr, or as fields beside the summary) and a test asserts
   it.
2. **The `X-Slice-Summary` header can pass what proxies accept.** 8,447 bytes for a done
   job of 25 warned parts with 20-character names, 17,467 with 200-character names
   (measured with the real Orca). Many reverse proxies refuse a response whose headers pass
   4 or 8 KB, and the fetch of a good sliced file would then fail. Fixed when the summary
   has a body of its own (for example in the final progress report or a
   `GET /slices/<job>/summary`) and the header is dropped or capped, with a test at 25
   warned parts.
3. **One kind of damage to a sliced file is reported as a bug.** `read_summary` catches
   `BadZipFile` and `OSError` when it opens the archive, but `zipfile` raises
   `NotImplementedError` for a directory entry that asks for an unknown zip version (3 of
   12,493 single-byte flips; "zip file version 23.5"). The job then fails as
   `slice.unexpected` ("The slicer failed unexpectedly.", not retryable) instead of
   `slice.unreadable_output`, and after a timeout or a watchdog stop it hides the stop's
   own code. Fixed when that open catches `_ZIP_READ_ERRORS` like the module's other three
   readers, with a test using such a file.
4. **`slicer.slice_plate` and `slice_stl` trust whatever sliced file is in the output
   folder.** Called with a folder that already holds a complete `plate.gcode.3mf`, and
   stopped by a timeout or the watchdog before Orca writes anything, they deliver the old
   file with a `stop_note` (evidence: `probe_settle.py` case 3, stopped after 0.029 s,
   "DELIVERED"). Before ruling 2 a stop always failed, so this is new. The slice service
   itself is not exposed: `slice_plate_job`, the command line and the HTTP face always
   slice in a new scratch folder. Fixed when the two functions remove an existing archive
   (and `result.json`) before starting Orca, or refuse a folder that has one, with a test.
5. **The reported peak can be the slice service's own memory, not Orca's.** `ru_maxrss`
   survives `exec`, so it starts at the resident memory of the service process at the
   moment it forks. Evidence: `/bin/true` run by `run_process` from a process holding
   400 MB reported `peak_rss_kb` 440,216 and `over_ceiling()` true at a 300 MB ceiling.
   With the service at its size after import (46 MB measured, under the 124 MB the
   smallest real slice here peaked at) the figure is Orca's; it becomes wrong only when the service process is larger than Orca's peak, and
   a false `memory_note` needs the service above the ceiling. The guide's "the peak
   reported is the true peak" should read "never under the true peak". Fixed when the
   guide says so, or the peak is taken from the watchdog's readings plus a final reading
   at exit.
6. **The memory ceiling setting accepts digits that are not ASCII.**
   `PENGUIN_SLICE_MAX_PEAK_MB="²"` raises `ValueError` in `limits.max_peak_mb`, so every
   plate job fails (`slice.unexpected`, HTTP 500); `"٣"` is read as 3 MB; a 30-digit number
   is accepted. An operator's typo only. Fixed when the setting is matched with
   `[0-9]{1,6}` and anything else falls back to the default with a log line.

## Open at commit

For the owner. Each item stands on its own; none blocks the commit.

1. **A stop note is not shown on the command line.** When the service stops Orca for a
   timeout or for memory just after Orca finished its file, the file is delivered, and the
   note saying so reaches the server log of the HTTP face but is not printed by
   `python -m penguin_slice slice`. A person slicing by hand would not know the slice
   touched the limit. Likelihood: rare (the window is about 30 ms of a slice). Fix: print
   the notes with the summary; small.
2. **The summary header of a sliced file can be too large for a proxy.** The summary
   travels in an HTTP header; with 25 different parts that each carry a warning it reaches
   8 to 17 KB, and a proxy in front of the service may then refuse the download of a good
   file. Likelihood: low (needs many distinct warned parts on one plate, and a proxy with
   a small limit). Fix: serve the summary as a body; small, but it changes the HTTP face
   and its client.
3. **A rare kind of damaged sliced file is reported as "The slicer failed unexpectedly."**
   instead of "The sliced file the slicer wrote is damaged.", and is marked not worth
   retrying when a retry would work. Likelihood: very low (needs a specific corrupted byte
   on disk). Fix: one line and a test.
4. **A direct caller of `slicer.slice_plate` that reuses an output folder can be handed an
   old sliced file** if a timeout or a memory stop ends the new run early. Students cannot
   reach this: the service always uses a new folder. It matters only to someone writing a
   new script on top of `slicer.py`. Fix: remove an existing archive before starting Orca;
   small.
5. **The peak memory in the log can be overstated** when the service process itself is
   larger than Orca's peak, because the kernel's figure includes the service's memory at
   the moment it starts Orca. Nothing is refused or stopped because of it; a support
   reading could be misled on small plates on a large service. Likelihood: low. Fix: say
   "never under the true peak" in the guide, or take the peak from the watchdog alone;
   small.
6. **A mistyped memory ceiling can stop every slice.** `PENGUIN_SLICE_MAX_PEAK_MB` set to
   a superscript or other non-ASCII digit makes every plate job fail with an unexpected
   error, and an Arabic-Indic digit is taken as a tiny ceiling. Likelihood: very low, and
   only at set-up. Fix: accept ASCII digits only; one line.
7. **The next Orca release cannot be taken yet.** `make upgrade-orca VERSION=2.5.1`
   downloads, verifies and pins, then stops: 2.5.1 ships the Bambu Lab profiles packed in
   one file (`BBL.opc`) that the profile flattening script cannot read. The guide records
   this and going back to 2.4.2 works. Until the script learns that format the service
   stays on 2.4.2. Certain to matter at the next upgrade. Fix: teach
   `scripts/flatten_orca_profiles.py` to read the packed profiles (size unknown until the
   format is examined), a strand of its own. Separately, the upgrade command stops when a
   patch exists instead of applying it, because applying one means building Orca from
   source; that is the owner's decision.
8. **The guide does not say the service must run as one process.** `serve` uses Flask's
   development server and keeps its jobs in that process's memory; behind a server that
   starts several workers, a client would lose its job. Likelihood: only at deployment.
   Fix: two sentences in the guide, or a production entry point when hosting is chosen.
9. **A thin, tall part can fail with only "The slicer could not slice this plate."** Orca
   keeps the real reason (floating regions and similar critical warnings) in its debug log
   only, so the student gets the general sentence and the remedy "Try another orientation
   or other print settings". Seen with a 0.3 x 0.3 x 300 mm needle. Likelihood: occasional
   with unusual parts. Fix: the proposed patch to Orca in `slice/patches/orca/README.md`
   (needs a source build, the owner's decision), or reading Orca's debug log on failure.
10. **Ctrl-C in the last instant of a command-line slice delivers the file** with exit 0
    instead of the `cancelled` report, because Orca had already finished. Harmless (the
    file is correct), but the guide's sentence about Ctrl-C is not exact for that instant.
    Through the HTTP face a cancel always ends `cancelled`. Fix: apply the cancel in the
    command as the job pool does, or amend the sentence; small.
